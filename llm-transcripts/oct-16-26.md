## The general shape of the gap

The official client is two kinds of thing:

- **Data the program reads**: MPQ archives holding DBC tables, M2, WMO, ADT,
  BLP, sounds, fonts, and the whole default interface written as Lua and XML
  (FrameXML, GlueXML). We can parse all of it, and the project already does for
  most formats.
- **The program itself (`Wow.exe`)**: the rules for *what to do* with that data.
  These include formulas, timings, the order things happen in, which choice wins
  when two apply, and the meaning of the numbers inside the data.

A useful way to say it: **the data files are nouns, and the exe holds the
verbs.** A DBC row says a spell has a precast visual, a missile model and an
impact visual. Only the exe knows that the precast loops until the cast bar
finishes, that the missile travels in an arc of a certain shape, and that the
impact fires when the missile reaches the target's chest attachment and not its
feet.

So the describer is mostly looking for **behavior**: inputs, outputs, constants,
timings and ordering. They aren't looking for structure.

One shortcut first. **AzerothCore already contains some client constants**,
because the server has to agree with the client to check its movement and spell
ranges. Gravity, jump speed, run, swim and flight speeds, melee and interact
reach, and the update-field layout are all in its source. Read those from AC
before sending anyone to the exe.

## What only the program knows, by area

## 1. The interface runtime (largest gap; docs/006)
The default UI is data, but it calls about two thousand functions that exist
only in C inside the exe.
- **The Lua API**: what each global function (unit health, spell info,
  action-bar queries…) returns, in what order, and what it returns for edge
  cases (no target, out of range, not yet cached).
- **Widget methods**: every method on frames, textures, font strings, scroll
  frames, sliders, edit boxes and models.
- **Events**: the full list, the arguments of each and their order, and **when**
  each fires relative to the others. For example, does the target-changed event
  come before or after the unit's health update in the same frame?
- **The layout engine**: how anchor points resolve, what happens with circular
  anchors, effective scale (a child's scale multiplied by its parents'), frame
  strata and levels, clipping, text wrapping and truncation, and how texture
  coordinates behave.
- **The per-frame order**: the per-frame update callbacks against event
  dispatch, and which frames update first.
- **The security system**: "taint" (marking anything addon code touched),
  protected functions, combat lockdown, and actions that require a real key
  press or click. You've said addons must run unchanged, so this is required.
- **The XML loader**: inheritance from templates, the virtual-frame rules, and
  what it does with errors.
- **Saved variables**: the exact format written to disk and when.

## 2. Movement and physics (issues 801, 802)
- Gravity, jump height, terminal velocity, how fall time is measured (the server
  works out fall damage from what the client reports).
- **The steepest walkable slope**, step-up height, and sliding down slopes that
  are too steep.
- The shape and size of the collision body per race and model. Some of this is
  in a DBC; how it's used is code.
- How the client decides between swimming and walking (water depth compared with
  body height), and getting out of water.
- **How often movement packets go out**: the heartbeat interval while moving,
  and which changes send a packet straight away.
- Moving on transports such as boats and zeppelins: coordinates relative to the
  vessel, getting on and off.
- **Smoothing other players and creatures between packets**: how far ahead the
  client guesses, and how it corrects when a guess turns out wrong.
- Turning speed, the backpedal speed ratio, strafing, and knockback arcs.

## 3. Camera (issue 207)
- Follow distance, zoom limits and zoom speed, pitch limits.
- What happens when the camera hits terrain or a building, and how it eases back
  out.
- Mouse-look sensitivity, and smoothing as the camera swings behind a moving
  character.
- Which settings in Config.wtf affect any of this.

## 4. Rendering rules (issues 302–310, 401–404)
The formats are documented. The *meaning* of some fields isn't.
- **Choosing the drawing recipe for M2 batches**: how a batch's texture-unit and
  blend-mode combination maps to the compiled shader used. The shaders
  themselves sit in the MPQs as compiled bytecode, but the choice of shader is
  made in code.
- The fog formula, and how the many Light.dbc values blend with distance from
  each light and with time of day.
- Sky dome geometry, and how the stars, sun and moon are placed.
- How terrain alpha layers combine, and how the baked terrain shadows are
  applied.
- How water animates and how its surface is shaded.
- Level-of-detail cutoffs and the distances at which small objects stop being
  drawn.
- **Particle and ribbon simulation**: M2 gives the parameters, the code gives
  the update formula. wowdev covers much of this, so check there first.

## 5. Characters and animation (issues 402, 404)
- **Character skin compositing**: the exe holds the pixel rectangles where arm,
  chest, leg and other texture pieces are pasted onto the body texture. This is
  one of the clearest "only in the program" facts.
- How item display info turns into which geosets (mesh pieces) are shown or
  hidden: the gloves, boots, cloak and robe rules, and which item wins when two
  items claim the same body area.
- **Which animation plays when**: walk, backpedal, strafe, combat stance, jump
  start, loop and land, emotes. Also the fallback chain when a model lacks an
  animation. Part of this is in a DBC, part is code.
- How one animation blends into the next, and how long the blend takes.
- Where weapons, shields and spell effects attach, and how mounts and vehicle
  seats position the rider.

## 6. Spell visuals and feedback
- **The order of a spell visual's stages**: precast, cast, channel, missile,
  impact, and the state left on the target afterwards.
- Missile flight: its speed (Spell.dbc), the **shape of its arc** (code), and
  the point it aims at on the target.
- When the client plays cast sounds, and when it shows floating combat text.

## 7. Text the client builds itself
- **Spell description tokens**: the little grammar of `$s1`, `$d`, `$o1`,
  `$/10;s1`, `$lsingular:plural;` and so on that turns DBC text into tooltip
  text. This lives entirely in code.
- Chat links (`|H…|h`), color codes, and the syntax of the in-text icons and
  textures.
- How numbers, durations and money are formatted in each locale.

## 8. Choices the client makes on the player's side
- **Tab targeting**: the cone in front of the player, the maximum distance, the
  sort order, and when it starts over.
- Choosing what's under the mouse (a ray cast against models, with or without
  the bounding boxes).
- Range checks that color action buttons red, which the client works out
  locally.
- How a unit's color is chosen from faction, hostility and tapped status.
- Click-to-move, auto-run, the interact distance, and auto-loot.

## 9. Sound (docs/007)
- The 3D falloff formula, and how many sounds can play at once and which ones
  wait (sound entries carry a priority, the code enforces it).
- Zone music and ambience changes: fade timing and what triggers them.
- Footstep sounds: ground type × animation event, with the table in data and
  the triggering in code.

## 10. Settings, caches and startup
- **The full Config.wtf setting list**: every setting's name, default value, and
  what it actually changes. There are hundreds.
- The format of the cache files in the WDB folder (creature, item and quest
  caches).
- **The order things happen at login and when entering the world**: what is
  loaded before the loading screen ends, and what the progress bar measures.
- What the client does on disconnect, when it reconnects, and how it handles a
  failed login.

## 11. The order of one frame
How the original sequences network → objects → movement → animation →
interface → drawing within one frame. Small differences here show up as
one-frame lag or flicker, especially in addons. It matters for the clock and
work-station issues you just finished (110e, 110g).

## Before writing a new issue

1. **Search first, including `issues/completed/`.** Grep the issue tree for
   the feature's nouns, not just the likely title. A completed issue about the
   same machinery is reopened and extended rather than duplicated: history is
   more useful stacked vertically in one file than spread across several.
2. **Pick the phase by what the work builds on**, not by when it is being
   done. Lower numbers are foundations; later issues depend on earlier ones.
3. **Take the number from the tool:** `validate-issues <project> --next
   <phase>`.
   It reads the project's own naming shape (522, 1001, 9-007, A04) and never
   reuses a number that a completed file already holds.
4. **Write the blueprint** with the three sections CLAUDE.md requires, plus
   link fields in the shape the project already uses (look at a neighbour).
   Name related functions, structures and files instead of pasting code.
5. **Check it:** `validate-issues <project> --file <new-issue>`, and fix what it
   reports on the new file. If the new issue blocks or is blocked by others,
   add the matching line to the other side too.

## While working

- Keep **Current Behavior** true. It is the only section that changes while
  an issue is in progress; rewrite it in place rather than appending a log.
- A question that surfaces is written into the issue (an "Open questions"
  section) and then asked. An issue with an unanswered question is in
  progress, not done.
- Anything discovered that changes another issue's assumptions is written into
  that issue now, not at completion.

## Splitting into sub-issues

Split when an issue holds work streams that could be built, tested or reviewed
separately, or when it cannot be finished in one sitting. Do not split an issue
that is already one mechanism. When splitting, produce and then write out:

1. **A table** — `| ID | Name | Dependencies | Description |`, where ID is the
   parent number plus a lower-case letter (103a, 103b), Name is dash-separated
   lower-case words, Dependencies is "None" or sibling IDs.
2. **The rationale** — the distinct work streams, why one issue cannot hold
   them, what splitting buys.
3. **The execution order** — a small dependency graph, e.g.
   `103a (foundation) → 103b (needs 103a) → 103c (parallel with 103b)`.

Each row becomes a file `{parent}{letter}-{name}.md` with the three sections.
The parent keeps its blueprint and gains a short list of its sub-issues; the
analysis itself is not appended to the parent (that would be worklog, not
blueprint). Run `validate-issues` afterwards: it reports orphaned sub-issues
and one-sided links.

## Completing an issue

An issue is complete only when nothing in it is deferred and no open question
is unanswered. Then, in this order:

1. **Run the project's tests.** A fixed bug gets a test that would have caught
   it.
2. **Rewrite the issue as the blueprint of what was built**: Current Behavior
   states the built system; steps name the real functions and files; decisions
   not taken are stated with their reason. Poetry the owner wrote during the
   work goes into the issue verbatim.
3. **Move it** into `issues/completed/` (`git mv`, so the history follows).
4. **Update `issues/phase-<N>-progress.md`** for that phase. Take counts from
   `progress-dashboard.lua <project> -m`, or better, name the command instead
   of copying numbers that will go stale.
5. **Update related issues** whose Current Behavior or assumptions changed.
6. **Run `validate-issues <project>`** and fix new findings that the change
   caused. Findings older than the change are reported to the owner, not
   silently fixed in passing.
7. **Commit** as below.

## Committing

The rule (CLAUDE.md): a commit carries exactly the lines this session wrote —
never another session's work, even if it sits in the same file — and every
changed transcript of the commit's projects rides along — the session's own
project folder and the projects of the files it commits — this
conversation's and any other's left behind (a session that committed, talked
on and quit), so each project's story in git stays whole.

Commit small and often: each piece as soon as it is done and checked, not a
pile at the end.

1. Optionally preview: `stage-own-changes <repo>` lists what would be taken
   and what left out, and writes nothing.
2. Commit: `commit-own-changes <repo> -F -` with the message on standard
   input. It builds the commit on a private staging list from this session's
   own lines (the edit ledger the edit hook keeps) plus those transcripts, and
   never touches the shared staging area, so nothing another
   session has staged can ride along. Plain `git commit` is refused by the
   commit gate.
3. Message style: say what the software now does, in plain English and by
   mechanism or analogy; mention any extra changes and why. No function names.

**When it stops or leaves something out.**

- **A tangled ("mixed") block** means another session changed lines right
  next to or on top of yours. Nothing is committed. Tell the owner which file
  and line; decide together what that region should say. `--leave-mixed`
  commits your other blocks meanwhile.
- **Lines that are yours but were written by a route the ledger could not see**
  (a script you ran, a generator, `sed`, a rename): record them with
  `claim-own-change <file>` and say so in the commit message.
- **Nothing to commit, but the work is there**: an earlier session wrote it
  and ended, or the machine rebooted and emptied the ledgers. Look first with
  `adopt-left-behind-changes <repo> --dry-run -- <path>...`, then adopt and
  commit one batch at a time with `commit-own-changes <repo> -F - --
  <path>...`. Lines reported as **held** belong to another session. Take them
  (`--from <session>`) only if that session has finished, and ask the owner
  if unsure. Say in the commit message that the work was adopted and from
  whom. This is the route for a left-behind backlog, not the token.
- **A warning about the shared staging area** means someone had staged that
  file by hand in a way that overlaps your commit; their entry was left alone.
  Tell the owner.

The one-time permission tokens (`/tmp/claude-allow-*`) belong to the person.
Never create one; if a gate names a token, relay the gate's message and let
the owner decide.

## What I meant by "does clean-room cover code?"

Clean-room works by keeping two kinds of worker apart:
- The **describer** reads the decompilation and writes facts into docs/057.
- The **builders** write the client's C code from those facts and have never
  seen the decompilation.

The separation is the whole legal value. If one person or session reads the
decompilation and then writes the matching C, that C can carry the original's
shape even without meaning to.

For us, the "workers" are mostly Claude sessions, and a session's memory is its
conversation. So the question is really two rules:
1. A conversation that has read the decompilation never writes client code
   afterwards.
2. The decompilation's copy lives somewhere a builder session won't find by
   accident: outside this project's folder, and outside every folder a builder
   searches.

Is that the rule you want? It's open question 3 in the page.
